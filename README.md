# Volatility Readout

A Go backend + web dashboard that watches Deriv's classic Volatility Indices
(R_10, R_25, R_50, R_75, R_100) and shows you, live:

- **Digit frequency** for each index — which last-digit is currently over/under
  represented, color-coded, for Over/Under and Even/Odd contracts
- **Tick momentum** — the recent up/down lean, for Rise/Fall
- A **"Connect Deriv account"** login so the dashboard can show your balance
- A **backtest panel** that replays real historical ticks to tell you honestly
  whether a given rule actually beats chance, before you risk anything on it

This build is **signals + monitoring only** — it never places a trade. You
watch the dashboard and trade manually on Deriv's own site or app. Auto-trading
was deliberately left out of this version (see "What this deliberately does
not do" below).

## Read this first: what the tool can and can't tell you

Deriv states openly that its Volatility Indices are generated by an internal
random-number model, not real market supply and demand. That means:

- Each tick's last digit is close to an independent random draw. A digit
  being "cold" (rare recently) does not make it more likely next time, and a
  digit being "hot" does not make it more likely to keep appearing either —
  both are the gambler's-fallacy and hot-hand reasoning you'll see in
  TikTok/YouTube "strategy" videos, and neither has a mathematical basis on a
  genuinely random source.
- Short-term price "momentum" on a synthetic index is similarly not
  something you should expect to persist.

So what is this tool actually for? It's an honest **instrument**, not an
oracle:
- The live panels show you the *current* state of the distribution, which is
  occasionally useful context and is exactly what those colorful TikTok tools
  show — this build is transparent about the fact that it's descriptive, not
  predictive.
- The **backtest panel is the important part**. It replays real historical
  ticks through the same trackers and tells you the *actual* win rate of
  betting on "hot continues", "cold is due", momentum continuation, and
  momentum reversion — compared to the true baseline (10% per digit, 50% for
  even/odd and rise/fall) with a standard-error band. Run it before trusting
  any rule. Expect most rules to land close to baseline — that's the correct,
  honest answer for a fair random process, not a bug.

## What this deliberately does not do

- It does not place trades. You saw a signal, you decide, you trade manually.
- It does not claim a working "strategy" that predicts the next digit or
  tick — no tool honestly can, for a genuinely randomly generated feed.
- Auto-trading and per-account risk controls (stake limits, daily loss caps)
  were intentionally scoped out of this build. Add them deliberately, later,
  only once the backtest panel has shown you something worth automating.

## Architecture

```
Deriv public feed (ticks)  →  ingestion.Feed  →  signals.Engine  →  Postgres (history)
                                                              ↘
                                                          httpapi.Hub → browser (WebSocket)

Browser  →  /auth/deriv/login  →  Deriv OAuth  →  /auth/deriv/callback → session cookie
Browser  →  /api/backtest  →  backtest.Run (fetches ticks_history, replays rules)
```

- `internal/deriv` — minimal client for Deriv's classic WebSocket API
  (`wss://ws.derivws.com/websockets/v3`, the same one DTrader itself runs on)
- `internal/ingestion` — one shared public connection subscribed to ticks for
  all 5 symbols (market data doesn't need auth, so it's shared across all users)
- `internal/signals` — the digit-frequency and momentum trackers, and the
  engine that turns threshold crossings into discrete `Signal`s
- `internal/backtest` — replays real historical ticks and scores six betting
  rules against their theoretical baseline
- `internal/authflow` — Deriv's OAuth login redirect + callback parsing
- `internal/store` — Postgres persistence (users, connected accounts, sessions,
  signal history)
- `internal/httpapi` — the HTTP/WebSocket server and dashboard routes
- `web/` — the dashboard frontend (plain HTML/CSS/JS, no build step)

## Setup

### 1. Prerequisites

- Go 1.22+
- Docker (for local Postgres) — or point `DATABASE_URL` at any Postgres you already run

### 2. Register a Deriv application (this is "connecting your account" set up)

This is the part that lets the dashboard log users in with their real Deriv
account, the same way DTrader itself works:

1. Log in at [app.deriv.com](https://app.deriv.com) with your Deriv account.
2. Go to **Settings → API token** page, then find **"Manage applications"**
   (also linked from developers.deriv.com) and register a new application.
3. Fill in:
   - **Name**: anything, e.g. "Volatility Readout"
   - **Redirect URL**: `http://localhost:8080/auth/deriv/callback` for local
     testing (change this to your real domain once deployed — it must match
     `OAUTH_REDIRECT_URL` exactly)
   - **Scopes**: at minimum `read` (for balance/account info). You do not
     need `trade` since this build never places orders.
4. Save it and copy the **App ID** it gives you — that's your `APP_ID`.

### 3. Configure

```bash
cp .env.example .env
# edit .env: paste your APP_ID, set OAUTH_REDIRECT_URL, generate APP_SECRET_KEY:
openssl rand -base64 32
```

### 4. Start Postgres and the server

```bash
docker compose up -d
export $(cat .env | xargs)
go run ./cmd/server
```

Open `http://localhost:8080`. You should see the five symbol panels start
updating within a few seconds as ticks arrive. Click **"Connect Deriv
account"** to log in with your real Deriv account and see your balance
alongside the signals.

### 5. Deploying (Render / Railway)

Same pattern as your other projects:
- Push this repo, add a Postgres addon, set the environment variables from
  `.env.example` in the service's dashboard (use your real domain for
  `OAUTH_REDIRECT_URL`, and update the app's registered Redirect URL on Deriv
  to match).
- Build command: `go build -o server ./cmd/server`
- Start command: `./server`

## Tuning the signal thresholds

`DIGIT_THRESHOLD_PCT` (default 4.0) controls how far a digit's frequency has
to drift from the 10% baseline before it's flagged hot/cold.
`MOMENTUM_THRESHOLD` (default 0.65) controls how one-sided the recent ticks
need to be before a Rise/Fall lean is flagged. Lower thresholds flag more
often (noisier); higher thresholds flag less often (fewer, stronger signals).
Change these in `.env` and re-run the backtest panel to see how a threshold
actually performs before trusting it live.

## Next steps if you want to extend this

- **Auto-trading**: add a `proposal` → `buy` call gated behind explicit
  per-user stake limits and a daily loss cap, using the account's stored
  token. Do this only after backtest results show something worth automating.
- **Telegram/webhook alerts**: subscribe to the same `onSignal` callback in
  `cmd/server/main.go` and fan out to another channel alongside the dashboard.
- **1-second Volatility indices**: add `1HZ10V` etc. to
  `internal/ingestion.Symbols` — everything else already generalizes.
